## Review

### Blocking Issues

**1. Planning round 3 plan omits NDF fixture from `fx-single-leg` despite documenting its exclusion.**  
The input brief requires mapping the full `fx-single-leg` group (7 fixtures), and the evidence shows 7 fixtures are in that group. The planner explicitly excludes `fx-ex07-non-deliverable-forward.xml` on grounds of “lack of cookbook evidence”, but the evidence packet shows this fixture *is* in the `fx-single-leg` group and has a corresponding CDM parallel file (`fx-ex07-non-deliverable-forward.json`). Its CDM summary contains `$.trade.product.economicTerms.payout[0].SettlementPayout.settlementTerms.settlementCurrency`, `$.trade.product.economicTerms.payout[0].SettlementPayout.settlementTerms.settlementDate.valueDate`, and `$.trade.product.economicTerms.payout[0].SettlementPayout.underlier.Observable` with `FxOptionCashSettlementTerms` and `FxFixingDate` structures, confirming it is a single-leg FX product. While NDF-specific mappings may be sparse, the expectation is to implement a *baseline* that handles `fxSingleLeg` root, trade header, parties, and payment amounts (including settlement currency/date) — which are covered by stable rules RULE-001, RULE-002, and RULE-005, and supported by other fixtures. Excluding the fixture from the test matrix breaks coverage and misaligns with `00-product-scope.json`.  
→ Must include `fx-ex07` in end-to-end tests with至少 a minimal mapping path that handles `payerPartyReference`, `receiverPartyReference`, `paymentAmount`, `valueDate`, and `settlementCurrency`.

**2. Java mapper plan is vague on handling multiple CDM settlements for NDF fixtures.**  
The NDF fixture evidence shows CDM output includes `$.trade.product.economicTerms.payout[0].SettlementPayout.settlementTerms.settlementCurrency` and `settlementDate.valueDate`, which differ from regular cash-settled single-legs where `settlementType = Cash` is implied but not explicitly set. The planner does not describe how `settlementCurrency` and `settlementDate` are derived in the current `SettlementTerms` model, nor how NDF-specific cash settlement terms are represented. While `SettlementTerms.settlementCurrency` appears in the CDM evidence, no cookbook rule currently covers this NDF-specific field; thus, the plan must either add an NDF-specific `FxSingleLegNdfTransformer` or extend the base transformer to handle `nonDeliverableForward/settlementCurrency` and fixings. Absence of this detail risks runtime gaps when the implementer hits NDF fields.  
→ Add a section describing settlement handling for NDF fixtures: how `settlementCurrency`, `fixingDate`, `fixingTime`, `fixingTime.businessCenter`, and `fixing/primaryRateSource` map to CDM settlement terms.

### Non-blocking Concerns

- **Product type taxonomy mapping**: The plan does not include a mapping for `productType`→`product.taxonomy` (e.g., “ForeignExchange_Spot_Forward”). While the CDM summary for single-legs uses `ISDA` taxonomy, no cookbook stable rule covers this. It should be added to the traceability table.
- **Date normalization scope**: The plan mentions date normalization for `tradeDate` but does not clarify whether `valueDate` (where present) is also normalized. NDF and forward fixtures contain `valueDate` in the FPML; CDM uses `settlementDate.valueDate`. Clarify whether date normalization applies to `valueDate`→`settlementDate.valueDate` as well.
- **`currentImplementationGroup` in plan header**: The plan header includes `currentImplementationGroup: fx-single-leg`, which is good. However, `00-product-scope.json` shows `currentImplementationGroup` is the *default* and `candidateNextGroups` include `fx-swap`, `fx-simple-option`. The plan should briefly acknowledge that future phases may target these groups.
- **Traceability table for `fx-ex07`**: The table is missing the NDF fixture. Add an entry showing applicable rules and any extensions.
