## Problem Statement

Financial analysts at this institution need to map new data formats to CDM (Common Domain Model). The existing tools require too much manual work and don't handle new formats efficiently. Analysts spend significant time understanding the semantic mapping, then either writing Java code themselves or waiting for developers to write it. The bottleneck is new format integration — mapping a new format to CDM can take weeks of analyst and developer time.

## Demand Evidence

Intrapreneurship project. Status quo confirmed: "existing tools require a lot of manual work and it does not handle new formats efficiently that do not exist. it requires too much manual work and brainpower to map them and then write the code." This is an internal productivity tool solving a known pain point within the financial institution.

## Status Quo

Existing tools have problems: manual mapping is slow, burns analyst brainpower, requires developer involvement for code generation. No efficient path for integrating new formats that aren't in the existing tool catalog.

## Target User & Narrowest Wedge

**Target User:** Financial analysts at this institution who map data formats to CDM.

**Narrowest Wedge:** Analysis tool that shows analysts what the proposed CDM mapping would look like, gets feedback, iterates. Prove the LLM + agentic skills can generate accurate mappings BEFORE building Java code generation.

## Constraints

- User spent 3 months researching FPML and CDM formats (on different machine/repo)
- Greenfield project (empty directory)
- Build-time environment (prototype) and production runtime (future Phase 2)
- Must work within financial institution's infrastructure constraints

## Premises

1. **REVISED:** The LLM, augmented with dynamically-loaded agentic skills for semantic resolution (party roles, temporality, cardinality, instrument-specific logic), can propose CDM mappings that analysts approve with minimal rewrites. (Originally: "LLM can learn patterns from examples." Revised after Codex challenged generalization risk. Skills encode domain expertise, LLM orchestrates.)

2. A financial analyst can evaluate the correctness of a proposed CDM representation without running it (review structure, confirm semantic correctness).

3. The Rosetta package can take an arbitrary CDM representation and generate correct Java code (solved code generation problem). [NOTE: This will be tested in Phase 2, not prototype.]

4. The bottleneck is new format integration, not maintaining existing mappings.

## Approaches Considered

### Approach A: Analyst Copilot with Skill-Augmented Agent (CHOSEN)
**Summary:** Streamlit/FastAPI UI. Analyst uploads new format + schema. Agent with dynamically-loaded skills (party-resolver, temporal-mapper, cardinality-checker) proposes CDM mapping field-by-field with confidence scores. Analyst reviews, edits, approves. Export to Rosetta-ready JSON. Skip the Java generation in prototype.

**Effort:** M (4-6 weeks for prototype)
**Risk:** Medium — skill orchestration complexity, need to build 3-5 core skills

**Pros:**
- Validates the core hypothesis (do agentic skills improve mapping quality?)
- Analysts see value immediately (review interface)
- Composable: add more skills over time
- Fast path to first value

**Cons:**
- Doesn't prove the Java generation step works (deferred to Phase 2)
- Skill routing logic could get complex
- Requires building multiple skills upfront

**Reuses:** 3 months of FPML→CDM research becomes skill training data and skill documentation

### Approach B: Full Two-Stage Pipeline (Mapping + Codegen)
**Summary:** Build both agents. Stage 1: skill-augmented mapping agent (like Approach A). Stage 2: Java coding agent that takes approved CDM + Rosetta package → generates JAR. Connects the full workflow end-to-end.

**Effort:** L (8-12 weeks)
**Risk:** High — two complex agents, Rosetta integration, Java generation verification

**Pros:**
- Proves the full value prop (analyst approval → production JAR)
- No manual Java writing step
- Complete automation of the workflow

**Cons:**
- Long time to first value
- If Stage 1 doesn't work, Stage 2 is wasted effort
- Rosetta package integration is unknown complexity
- Over-commits before validating core hypothesis

**Reuses:** Rosetta package (if Premise 3 holds)

## Recommended Approach

**Approach A: Skill-Augmented Analyst Copilot**

Rationale: Tests the core hypothesis (agentic skills improve mapping quality) without over-committing to Java generation before we know the mapping stage works. Gets to first value faster (4-6 weeks vs 8-12 weeks). If mapping works, Java generation becomes Phase 2. If mapping doesn't work, we learned that early without wasting 8 weeks on code generation.

Codex's prototype recommendation aligns: prove retrieval + constrained generation reduces analyst time without collapsing trust, then expand.

### Architecture

**Components:**
1. **Upload Interface** (Streamlit or FastAPI + React)
   - Analyst uploads new format sample (XML/JSON)
   - Optional: upload schema/documentation
   
2. **Format Parser & Normalizer**
   - Parse XML/JSON into intermediate graph representation
   - Extract field names, types, structure, relationships
   
3. **Skill Library** (dynamically loadable)
   - `party-resolver`: Maps party role fields to CDM party structures
   - `temporal-mapper`: Handles date/time fields, event lifecycles
   - `cardinality-checker`: Infers 1:1, 1:N, N:M relationships
   - `instrument-resolver`: Handles instrument-specific edge cases
   - `unit-normalizer`: Currency, quantity, unit conversions
   
4. **Mapping Agent** (LLM with tool use)
   - For each source field: invoke relevant skill via tool calling
   - Skills return: CDM target path + confidence + reasoning
   - Generate confidence score + evidence (which mapping rules were applied, which skill was used)
   - **NOTE:** Removed RAG/vector DB - skills ARE the executable knowledge
   
5. **Review Interface**
   - Display proposed mapping field-by-field:
     - Source field name/path
     - Target CDM path
     - Transformation note
     - Confidence score (0-100)
     - Supporting evidence (retrieved examples, skill invoked)
     - Unresolved questions flagged
   - Analyst can: approve, edit, reject, annotate each mapping
   
6. **Export Module**
   - Approved mapping → Rosetta-ready JSON/YAML package
   - Audit trail: who approved, when, what was changed

**Tech Stack: (UPDATED 2026-04-17)**
- **Runtime:** Bun (fast startup, built-in bundler/test runner)
- **Language:** TypeScript (type safety end-to-end)
- **Framework:** Hono + `@hono/zod-openapi` (lightweight, OpenAPI docs)
- **Validation:** Zod (runtime + compile-time validation)
- **LLM Provider:** OpenRouter (model flexibility, fallback routing)
- **Storage:** SQLite (prototype). Upgrade to PostgreSQL if audit immutability required.
- **XML/JSON Parsing:** fast-xml-parser
- **UI:** Simple HTML + HTMX for prototype. React if Phase 2 requires polish.

**"Dynamically-loaded skills" Implementation:**
Skills implemented as TypeScript functions with Zod schemas, registered in a skill registry. Agent invokes skills via Claude's tool-calling (function calling) through OpenRouter. "Dynamic loading" means skills can be added to registry without changing agent orchestration code. Each skill auto-registers on import.

**Skill Routing (Hybrid Precedence):**
1. Rule-based triggers run first (keyword/type matching):
   - If field contains "party", "counterparty", "buyer", "seller" → invoke party-resolver
   - If field type is date/datetime or name contains "date", "time", "maturity" → invoke temporal-mapper
   - If field is array or has cardinality annotations → invoke cardinality-checker
2. Agent can invoke additional skills via tool-calling if context suggests semantic ambiguity
3. Agent cannot suppress rule-triggered skills

### Data Requirements

1. **Training corpus:** Collection of existing FPML→CDM mapping examples (from user's 3-month research)
2. **Skill definitions:** Document each skill's input/output contract, when to invoke it
3. **Test formats:** 2-3 new formats NOT in training corpus for validation

## Open Questions

1. **What is the implementation complexity of each skill?** Assignment findings will determine whether 4-6 weeks is realistic or if skill scoping needs adjustment.

2. **What is the exact schema for Rosetta-ready JSON?** Need documentation from Rosetta package maintainers.

3. **Does audit trail need compliance-grade immutability?** If yes, use append-only log (PostgreSQL with write-once tables) instead of SQLite.

4. **Schema versioning:** CDM schema evolves. How do we handle version mismatches between training examples and current CDM version?

5. **What are the validation format selection criteria?** Specify: (1) structurally different from FPML, (2) contains edge cases requiring at least 3 skills, (3) has known ground-truth CDM mapping for accuracy measurement.

## Success Criteria

**Prototype success (4-6 weeks):**
- Analyst can upload a new format and get a proposed CDM mapping in < 5 minutes
- At least X% of proposed field mappings approved by analyst without major rewrites (threshold TBD based on Assignment findings — initial target 70%)
- **Major rewrite defined as:** changing the target CDM path or transformation logic. Minor edits (adjusting confidence annotation, adding notes) don't count as rewrites.
- Confidence scores correlate with analyst approval (high confidence = higher approval rate)
- Export generates valid Rosetta-ready format (even if we don't run Rosetta in prototype)

**Phase 2 success (Java generation):**
- Approved mapping → executable JAR via Rosetta package
- Generated code passes institution's validation tests
- End-to-end time (upload → production JAR) < 1 day (vs weeks today)
