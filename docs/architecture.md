## Executive Summary

**What we're building:** AI-powered analyst copilot that takes new financial data formats, proposes CDM mappings using agentic skills, and exports Rosetta-ready packages. Phase 1 prototype (4-6 weeks) validates mapping accuracy. Phase 2 (future) adds Java code generation.

**Core innovation:** Dynamically-loaded agentic skills encode domain expertise (party roles, temporal fields, cardinality, instruments, units). LLM orchestrates skills via tool calling. No vector DB. No RAG. Just executable knowledge + LLM orchestration.

**Tech stack:** TypeScript + Bun + Hono + Zod + OpenRouter

**Critical path:** Skills generated by Claude Code during planning phase from FPML 5.12 + CDM 6 documentation (see SKILL_GENERATION_PLAN.md for detailed process)

## Skills: The Core Innovation

### What is a Skill?

A skill is an executable function that encodes domain expertise. It takes a field description and returns a CDM mapping proposal with confidence and reasoning.

**Skill = Transformation Recipe from Research**

```typescript
// skills/types.ts
import { z } from 'zod'

export interface Skill {
  name: string
  description: string
  inputSchema: z.ZodSchema
  outputSchema: z.ZodSchema
  fn: (input: any) => any | Promise<any>
  triggers: {
    keywords?: string[]      // Field name contains any of these → trigger
    fieldTypes?: string[]     // Field type matches any of these → trigger
    patterns?: RegExp[]       // Field name matches regex → trigger
  }
}

// Base input/output schemas (all skills extend these)
export const BaseSkillInput = z.object({
  fieldName: z.string(),
  fieldValue: z.string().optional(),
  fieldPath: z.string(),
  fieldType: z.string().optional(),
  context: z.record(z.any()).optional()  // Extra metadata from parser
})

export const BaseSkillOutput = z.object({
  cdmPath: z.string(),                    // Target CDM path (e.g., "party.buyer")
  transformation: z.string(),              // Transformation note (e.g., "map_party_role")
  confidence: z.number().min(0).max(100),  // Confidence score 0-100
  reasoning: z.string()                    // Human-readable explanation
})
```

### Skill Registry Pattern

```typescript
// skills/registry.ts
import type { Skill } from './types'

const registry = new Map<string, Skill>()

export const registerSkill = (skill: Skill) => {
  console.log(`[Registry] Registered skill: ${skill.name}`)
  registry.set(skill.name, skill)
}

export const getSkill = (name: string): Skill | undefined => {
  return registry.get(name)
}

export const getAllSkills = (): Skill[] => {
  return Array.from(registry.values())
}

/**
 * Match skills to a field based on triggers.
 * A skill triggers if ANY of its trigger conditions match:
 * - Field name contains any keyword
 * - Field type matches any fieldType
 * - Field name matches any pattern
 */
export const matchSkills = (field: {
  name: string
  type?: string
  path: string
}): Skill[] => {
  const matched: Skill[] = []

  for (const skill of registry.values()) {
    if (shouldTrigger(field, skill.triggers)) {
      matched.push(skill)
    }
  }

  return matched
}

const shouldTrigger = (
  field: { name: string; type?: string },
  triggers: Skill['triggers']
): boolean => {
  // Check keywords
  if (triggers.keywords) {
    const lowerName = field.name.toLowerCase()
    if (triggers.keywords.some(kw => lowerName.includes(kw.toLowerCase()))) {
      return true
    }
  }

  // Check field types
  if (triggers.fieldTypes && field.type) {
    if (triggers.fieldTypes.includes(field.type)) {
      return true
    }
  }

  // Check patterns
  if (triggers.patterns) {
    if (triggers.patterns.some(pattern => pattern.test(field.name))) {
      return true
    }
  }

  return false
}
```

```typescript
// skills/party-resolver/logic.ts
import type { PartyResolverInput, PartyResolverOutput } from './schemas'

/**
 * Party Resolver Logic
 * 
 * RESEARCH NOTES:
 * - FPML uses <buyer>, <seller>, <counterparty>, <payer>, <payee>
 * - CDM uses party.buyer, party.seller, party.counterparty
 * - Edge case: <payer> can map to buyer OR seller depending on context
 *   - If context contains "premium" → buyer (buyer pays premium)
 *   - If context contains "settlement" → seller (seller receives settlement)
 * 
 * CONFIDENCE RULES:
 * - 95% for exact keyword match (buyer → buyer)
 * - 80% for contextual match (payer + premium → buyer)
 * - 50% for ambiguous (payer without context)
 */
export const partyResolverLogic = (input: PartyResolverInput): PartyResolverOutput => {
  const lowerName = input.fieldName.toLowerCase()
  const contextStr = JSON.stringify(input.context || {}).toLowerCase()

  // Exact matches (high confidence)
  if (lowerName.includes('buyer')) {
    return {
      cdmPath: 'party.buyer',
      transformation: 'map_party_role',
      confidence: 95,
      reasoning: 'Field name contains "buyer" → direct mapping to CDM party.buyer',
      partyRole: 'buyer'
    }
  }

  if (lowerName.includes('seller')) {
    return {
      cdmPath: 'party.seller',
      transformation: 'map_party_role',
      confidence: 95,
      reasoning: 'Field name contains "seller" → direct mapping to CDM party.seller',
      partyRole: 'seller'
    }
  }

  if (lowerName.includes('counterparty')) {
    return {
      cdmPath: 'party.counterparty',
      transformation: 'map_party_role',
      confidence: 95,
      reasoning: 'Field name contains "counterparty" → direct mapping to CDM party.counterparty',
      partyRole: 'counterparty'
    }
  }

  // Contextual matches (medium confidence)
  if (lowerName.includes('payer')) {
    if (contextStr.includes('premium')) {
      return {
        cdmPath: 'party.buyer',
        transformation: 'map_party_role',
        confidence: 80,
        reasoning: 'Field name "payer" + context contains "premium" → buyer pays premium → CDM party.buyer',
        partyRole: 'buyer'
      }
    }
    if (contextStr.includes('settlement')) {
      return {
        cdmPath: 'party.seller',
        transformation: 'map_party_role',
        confidence: 80,
        reasoning: 'Field name "payer" + context contains "settlement" → seller receives settlement → CDM party.seller',
        partyRole: 'seller'
      }
    }
    // Ambiguous case
    return {
      cdmPath: 'party.payer',
      transformation: 'map_party_role',
      confidence: 50,
      reasoning: 'Field name "payer" without clear context → ambiguous mapping, defaulting to CDM party.payer',
      partyRole: 'payer'
    }
  }

  if (lowerName.includes('payee')) {
    return {
      cdmPath: 'party.payee',
      transformation: 'map_party_role',
      confidence: 90,
      reasoning: 'Field name contains "payee" → direct mapping to CDM party.payee',
      partyRole: 'payee'
    }
  }

  // No match
  return {
    cdmPath: 'party.unknown',
    transformation: 'unknown_party_role',
    confidence: 0,
    reasoning: 'Field name does not match any known party role patterns',
    partyRole: 'unknown'
  }
}
```

### Iterative Refinement (Week 4+)

**Goal:** Improve skills based on real analyst usage.

**Process:**

1. **Log failures**
  - When analyst rejects a mapping, log: field input, proposed output, analyst's correction
  - Store in `failed_mappings` table

  - Commit updated skill
  - Restart service (Bun hot-reloads automatically in dev)

## Agent Orchestration

### LLM Client Abstraction

```typescript
// agent/client.ts
import Anthropic from '@anthropic-ai/sdk'
import { z } from 'zod'

export interface LLMMessage {
  role: 'user' | 'assistant'
  content: string
}

export interface LLMTool {
  name: string
  description: string
  input_schema: Record<string, any>  // Zod → JSON Schema
}

export interface LLMResponse {
  content: string
  tool_calls?: {
    id: string
    name: string
    input: Record<string, any>
  }[]
}

export interface LLMClient {
  call(params: {
    messages: LLMMessage[]
    tools?: LLMTool[]
    model?: string
  }): Promise<LLMResponse>
}

/**
 * OpenRouter client (wraps Anthropic SDK with OpenRouter base URL)
 */
export class OpenRouterClient implements LLMClient {
  private client: Anthropic

  constructor(apiKey: string, model: string = 'anthropic/claude-sonnet-4') {
    this.client = new Anthropic({
      apiKey,
      baseURL: 'https://openrouter.ai/api/v1'
    })
  }

  async call(params: {
    messages: LLMMessage[]
    tools?: LLMTool[]
    model?: string
  }): Promise<LLMResponse> {
    const response = await this.client.messages.create({
      model: params.model || 'anthropic/claude-sonnet-4',
      max_tokens: 4096,
      messages: params.messages,
      tools: params.tools
    })

    // Parse response
    const textContent = response.content.find(c => c.type === 'text')
    const toolCalls = response.content
      .filter(c => c.type === 'tool_use')
      .map(c => ({
        id: c.id,
        name: c.name,
        input: c.input
      }))

    return {
      content: textContent?.text || '',
      tool_calls: toolCalls.length > 0 ? toolCalls : undefined
    }
  }
}
```

### Main Orchestrator

```typescript
// agent/orchestrator.ts
import { getAllSkills, matchSkills, getSkill } from '../skills/registry'
import { getToolsFromSkills } from './tools'
import type { LLMClient, LLMMessage } from './client'
import type { Field } from '../parser/types'

export interface MappingProposal {
  sourceField: Field
  cdmPath: string
  transformation: string
  confidence: number
  reasoning: string
  skillInvoked: string
}

/**
 * Main agent logic: field → skill matching → invocation → proposal
 */
export class MappingAgent {
  constructor(private llmClient: LLMClient) {}

  /**
   * Generate mapping proposals for all fields
   */
  async generateMappings(fields: Field[]): Promise<MappingProposal[]> {
    const proposals: MappingProposal[] = []

    for (const field of fields) {
      const proposal = await this.mapField(field)
      proposals.push(proposal)
    }

    return proposals
  }

  /**
   * Map a single field to CDM
   * 
   * Process:
   * 1. Match field → skills (via registry triggers)
   * 2. Prepare LLM call with matched skills as tools
   * 3. LLM decides which skill(s) to invoke
   * 4. Execute skill(s)
   * 5. Return proposal
   */
  private async mapField(field: Field): Promise<MappingProposal> {
    // Step 1: Match skills
    const matchedSkills = matchSkills({
      name: field.name,
      type: field.type,
      path: field.path
    })

    if (matchedSkills.length === 0) {
      // No skills matched → return low-confidence generic mapping
      return {
        sourceField: field,
        cdmPath: `unmapped.${field.name}`,
        transformation: 'no_skill_matched',
        confidence: 0,
        reasoning: 'No skills matched this field',
        skillInvoked: 'none'
      }
    }

    // Step 2: Prepare tools
    const tools = getToolsFromSkills(matchedSkills)

    // Step 3: LLM call
    const messages: LLMMessage[] = [
      {
        role: 'user',
        content: `Map this field to CDM:
Field name: ${field.name}
Field type: ${field.type || 'unknown'}
Field path: ${field.path}
Field value (sample): ${field.value || 'N/A'}

Context: ${JSON.stringify(field.context || {})}

Available skills: ${matchedSkills.map(s => s.name).join(', ')}

Invoke the appropriate skill(s) to map this field to CDM.`
      }
    ]

    const response = await this.llmClient.call({
      messages,
      tools
    })

    // Step 4: Execute skill
    if (!response.tool_calls || response.tool_calls.length === 0) {
      // LLM didn't invoke any skills → fallback
      return {
        sourceField: field,
        cdmPath: `unmapped.${field.name}`,
        transformation: 'llm_no_tool_call',
        confidence: 0,
        reasoning: 'LLM did not invoke any skills',
        skillInvoked: 'none'
      }
    }

    // Take first tool call (could extend to multiple)
    const toolCall = response.tool_calls[0]
    const skill = getSkill(toolCall.name)

    if (!skill) {
      throw new Error(`Skill ${toolCall.name} not found in registry`)
    }

    // Execute skill
    const skillOutput = await skill.fn(toolCall.input)

    // Step 5: Return proposal
    return {
      sourceField: field,
      cdmPath: skillOutput.cdmPath,
      transformation: skillOutput.transformation,
      confidence: skillOutput.confidence,
      reasoning: skillOutput.reasoning,
      skillInvoked: skill.name
    }
  }
}
```

## Database Schema

```sql
-- storage/schema.sql

-- Uploaded formats (original XML/JSON)
CREATE TABLE uploads (
  id TEXT PRIMARY KEY,
  filename TEXT NOT NULL,
  content TEXT NOT NULL,          -- Original XML/JSON
  format_type TEXT NOT NULL,      -- 'xml' | 'json'
  uploaded_at TEXT NOT NULL,
  uploaded_by TEXT NOT NULL
);

-- Parsed fields (intermediate representation)
CREATE TABLE fields (
  id TEXT PRIMARY KEY,
  upload_id TEXT NOT NULL,
  name TEXT NOT NULL,
  type TEXT,
  path TEXT NOT NULL,
  value TEXT,
  context TEXT,                    -- JSON string
  FOREIGN KEY (upload_id) REFERENCES uploads(id)
);

-- Mapping proposals (generated by agent)
CREATE TABLE proposals (
  id TEXT PRIMARY KEY,
  upload_id TEXT NOT NULL,
  field_id TEXT NOT NULL,
  cdm_path TEXT NOT NULL,
  transformation TEXT NOT NULL,
  confidence INTEGER NOT NULL,     -- 0-100
  reasoning TEXT NOT NULL,
  skill_invoked TEXT NOT NULL,
  status TEXT NOT NULL,            -- 'pending' | 'approved' | 'rejected' | 'edited'
  created_at TEXT NOT NULL,
  FOREIGN KEY (upload_id) REFERENCES uploads(id),
  FOREIGN KEY (field_id) REFERENCES fields(id)
);

-- Approved mappings (analyst reviewed)
CREATE TABLE approved_mappings (
  id TEXT PRIMARY KEY,
  proposal_id TEXT NOT NULL,
  cdm_path TEXT NOT NULL,         -- May differ from proposal if edited
  transformation TEXT NOT NULL,
  approved_by TEXT NOT NULL,
  approved_at TEXT NOT NULL,
  notes TEXT,
  FOREIGN KEY (proposal_id) REFERENCES proposals(id)
);

-- Failed mappings (for skill refinement)
CREATE TABLE failed_mappings (
  id TEXT PRIMARY KEY,
  field_id TEXT NOT NULL,
  proposal_id TEXT NOT NULL,
  analyst_correction TEXT NOT NULL,  -- What analyst changed it to
  analyst_notes TEXT,
  failed_at TEXT NOT NULL,
  FOREIGN KEY (field_id) REFERENCES fields(id),
  FOREIGN KEY (proposal_id) REFERENCES proposals(id)
);

-- Exports (Rosetta-ready JSON)
CREATE TABLE exports (
  id TEXT PRIMARY KEY,
  upload_id TEXT NOT NULL,
  rosetta_json TEXT NOT NULL,      -- Full Rosetta JSON
  exported_by TEXT NOT NULL,
  exported_at TEXT NOT NULL,
  FOREIGN KEY (upload_id) REFERENCES uploads(id)
);

-- Audit trail
CREATE TABLE audit_log (
  id TEXT PRIMARY KEY,
  entity_type TEXT NOT NULL,       -- 'upload' | 'proposal' | 'export'
  entity_id TEXT NOT NULL,
  action TEXT NOT NULL,            -- 'created' | 'approved' | 'rejected' | 'exported'
  user TEXT NOT NULL,
  timestamp TEXT NOT NULL,
  metadata TEXT                    -- JSON string
);
```

```typescript
import { z } from 'zod'

        'multipart/form-data': {
          schema: z.object({
            file: z.instanceof(File),
            formatType: z.enum(['xml', 'json'])

  },

      content: {
        'application/json': {
          schema: z.object({

          })
        }
      }
    }
  }

export const uploadAPI = new OpenAPIHono()

uploadAPI.openapi(uploadRoute, async (c) => {
  const { file, formatType } = await c.req.parseBody()
  const content = await file.text()

  // Parse
  const fields = formatType === 'xml' 
    ? parseXML(content) 
    : parseJSON(content)

  // Save to DB
  const uploadId = crypto.randomUUID()
  await saveUpload({
    id: uploadId,
    filename: file.name,
    content,
    formatType,
    uploadedBy: 'analyst@company.com' // TODO: get from auth
  })

  await saveFields(uploadId, fields)

  return c.json({ uploadId, fieldsCount: fields.length })
})
```

## Appendix: Key Technical Decisions

### Why TypeScript over Python?

- Agentic skills = tool definitions, language-agnostic
- Zod → Claude tools cleaner than Pydantic → Claude tools
- Bun deployment simpler (single binary vs Docker)
- Type safety end-to-end (skills, API, LLM schemas)

### Why no Vector DB?

- Skills ARE the knowledge (executable, not retrieved)
- RAG is passive (retrieve text), skills are active (execute logic)
- Simpler: no embeddings, no chunking, no reranking
- Easier to debug: skill code visible, not black-box retrieval

### Why OpenRouter over direct Claude API?

- Model flexibility (test GPT-4, o1, Llama if Claude fails)
- Cost optimization potential (future: cheap model for routing)
- Fallback routing (Claude rate-limits → auto-failover)
- Abstracted client → easy to swap if we need extended thinking

### Why SQLite over PostgreSQL?

- Prototype simplicity (no separate DB server)
- Fast local development (no network latency)
- Sufficient for single-user prototype
- Easy migration path: same SQL, swap driver

### Why Hono over Express/Fastify?

- Lightweight (< 12KB)
- Built-in OpenAPI support (self-documenting API)
- Edge-ready (Bun, Deno, Cloudflare Workers)
- Fast routing (~2-3x faster than Express)
